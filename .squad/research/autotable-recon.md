## 3. Directory Layout

Frontend structure centers on a modular `src/` with clear separation: `types.ts` defines the domain model; `game.ts` orchestrates; `main-view.ts` manages three.js scene/camera/renderer; `object-view.ts` renders Things (tiles, sticks, markers) using instanced meshes; `world.ts` holds game state; `thing-group.ts` optimizes rendering via ThingGroup classes; `asset-loader.ts` loads textures/models from Blender-generated .glb files. Backend (`server/`) is minimal: `protocol.ts` defines WebSocket messages, base server loop handles game rooms and state sync. Build artifacts (SVG→PNG textures, .blend→.glb models) are generated by Makefile with Inkscape and Blender CLI.

## 4. Networking Model

**Central authoritative server** with **WebSocket protocol**.  
- Client connects via WebSocket to `localhost:1235` (or `/autotable/ws` via nginx proxy).
- Server maintains a key-value store of **collections** (match, things, seats, mouse, sound, dice, nicks).
- Client sends updates (e.g., "move tile to slot"); server validates and broadcasts to all players.
- **Rate limiting:** Mouse position updates capped at 10/sec; others sent immediately.
- **State reconciliation:** Full snapshot on join (`full: true`), then incremental updates.
- **Key concept:** BaseClient implements a local cache synchronized with server state; no peer-to-peer.

**Mouse sync example:** Waypoints sent every ~100ms with timestamps, client interpolates smoothly between them to hide latency (100ms delay introduced globally, negligible for non-real-time game).

## 5. Tile Rendering Approach

**Per-tile 3D models** generated via Blender export to .glb format, textured with SVG-derived PNGs (Inkscape → PNG).
- **Mesh structure:** Rounded-corner boxes (not flat sprites); individual face textures applied per material.
- **Optimization:** ThingGroup uses **InstancedMesh** to render dozens of tiles efficiently; one draw call per type (tile, stick, marker).
- **Backs/Faces:** Achieved through multi-material geometry; textures encode both tile front (face-up) and solid back (face-down) states. Rotation is managed via quaternion in `Place` object.
- **No atlas texture:** Each tile type has its own geometry and material slots in the .glb.
- **Selection highlight:** OutlinePass post-processing effect to outline selected tiles (bright yellow edge).

---

## 6. Physics Usage

**Zero physics engine.** Physics is **entirely state-driven**:
- Tiles do **not** tumble, collide, or bounce.
- Tiles **do not** fall; they are placed in slots at fixed positions.
- Tile picking is via **raycasting** (camera.ray → mouse coords).
- Dragging is **constrained**: tile follows mouse in the same horizontal plane (z = initial drag height).
- "Shift" mechanic (pushing adjacent tiles) is **slot-based logic** in the data model, not collision detection.

**Implication:** A **server-authoritative client could skip 3D rendering entirely** and render tiles as 2D cards at the slot positions. Physics is genuinely unnecessary; three.js is used only for orthographic/perspective visualization of a turn-based board game.

## 7. View Toggle

**Orthographic vs. Perspective camera mode**, toggled by:
- UI checkbox: `<input id="perspective">` (game.ts line `this.settings.perspective`)
- Keyboard shortcut: Press `'p'`
- **File/Function Reference:** `src/game.ts` → `updateSettings()` calls `this.mainView.setPerspective(bool)` → `src/main-view.ts` → `makeCamera(bool)` creates `OrthographicCamera` or `PerspectiveCamera` and adds it to the scene.
- **Animation:** 100ms smooth transition between views via `this.lookDown` Animation object.
- **Purpose:** Orthographic keeps top-down clarity; perspective adds immersion (harder to click far tiles).

## 9. Lessons to Copy

1. **Slot-based tile placement:** Modeling the board as named slots (hand, wall, discard, etc.) with allowed rotations and push relationships is elegant and avoids collision bugs. Automate push resolution when tiles rotate.

2. **State-driven architecture:** Tiles are data (Thing: index, slot, rotation, claim status), not physics objects. Clients receive state updates and animate to match. Makes networking and undo/replay trivial.

3. **WebSocket + key-value sync:** The "collection" abstraction (server-side key-value store, client caches it, sends deltas) is clean for turn-based games. No need for complex RPC or frame-by-step state.

4. **Mouse position as 3D data:** Syncing mouse waypoints (not pixel coords) makes multiplayer feel responsive. Interpolation between waypoints hides 100ms network latency.

5. **Instanced rendering:** ThingGroup using InstancedMesh scales to 100+ tiles with negligible GPU cost. Essential for smooth gameplay.

---

## 10. Lessons to Avoid

1. **Non-commercial asset licensing:** Using CC BY-NC-SA tiles locks the project into hobbyist territory. This is their only real constraint; don't repeat it.

2. **Makefile-based build pipeline:** Relying on Inkscape CLI and Blender CLI for asset generation is fragile in CI/CD. Consider embedded asset generation or pre-baked assets in version control (though they use Git LFS).

3. **Orthographic projection as primary view:** Players struggle with the far-bottom tile in the wall being hard to click. A higher camera angle, dynamic zoom, or scrollable viewport would be better. The perspective mode is a band-aid.

4. **No persistence or replay:** Game state lives only in server memory. If the server crashes, the game is lost. No replays, no spectating mid-game. For social gaming, adding a light PostgreSQL layer to persist games would be valuable.

5. **Limited UI customization:** The settings panel is minimal (theme, labels, perspective toggle). Accessibility features (colorblind tile variants, font scaling) are missing. Plan for these early.

---

## Summary

Autotable is a **minimal, well-scoped mahjong simulator** that prioritizes simplicity and social realism over automation. Its tech stack (TypeScript, three.js, Parcel, WebSocket) is mature and portable. The state-driven, slot-based game model is a solid pattern for turn-based multiplayer. However, its physics-free approach, non-commercial tile assets, and lack of persistence are not shortcomings for a social simulator—they are design choices reflecting the author's philosophy ("no rules, no automation, real-life feel").

**For mahjong-claw:** Adopt the slot-based model, key-value sync protocol, and instanced rendering. **Do not** adopt tile assets or assume physics is needed. Invest in original tile art from day one.
