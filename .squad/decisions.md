### 2026-08-05T23-44-30: Defect: special-context Big Wins (海底捞月/河底捞鱼/天和/地和/杠上开花/抢杠胡) on a plain Standard-shaped hand are scored as Small Win, not Big Win
**By:** audit
**What:** Defect: special-context Big Wins (海底捞月/河底捞鱼/天和/地和/杠上开花/抢杠胡) on a plain Standard-shaped hand are scored as Small Win, not Big Win
**References:** docs/rules/changsha-spec.md#4.2.2, docs/rules/changsha-spec.md#5.1, .squad/decisions.md:274, src/backend/src/Mahjong.Autotable.Api/Changsha/ScoringService.cs, src/backend/src/Mahjong.Autotable.Api/Changsha/WinDetector.cs
**Why:** AUDIT FINDING (origin/main @ 0dfd96a) — Changsha rules/runtime correctness audit.

ROOT CAUSE
`ScoringService.ClassifyWin(WinResult)` (src/backend/src/Mahjong.Autotable.Api/Changsha/ScoringService.cs, was ~line 141) decided Small vs Big Win purely from `win.Pattern`, mapping ONLY the four structural Big Wins (SevenPairs, AllPungs, FullFlush, NineTerminals) to BigWin and everything else to SmallWin via the `_ =>` default.

When a hand's structural shape is plain Standard but a contextual Big-Win flag fires (海底捞月 LastTileFromWall / 河底捞鱼 LastDiscardCatch / 天和 HeavenlyHand / 地和 EarthlyHand / 杠上开花 KongReplacementWin), the WinDetector sets the headline `Pattern` to that contextual enum (structural pattern was null). ClassifyWin's switch has no case for those enums → falls to `_ => SmallWin`. Likewise 抢杠胡 (RobbingKong) has no WinPattern at all (tracked via WinMethod/IsRobbedKong) so it was never Big-Win-classified unless the hand was independently a structural Big Win.

The WinDetector DOES compute Category=BigWin, but WinResult carries no Category field and ScoringService recomputes from Pattern, so the detector's decision is discarded.

IMPACT: In default SpecPure mode a contextual-only Big Win self-draw pays 1/2 instead of 3/4 (discard 1/2 instead of 6/7) — a real underpayment on the authoritative §5.1 payout. Contradicts spec §4.2.2 ("upgrade an otherwise-valid hand to Big Win pricing") and this decisions log (Phase I Wave 1: "score category = BigWin").

WHY UNTESTED: SpecialContextWinsTests only assert `AllPatterns` contains the enum; they never assert ScoreResult.Category or payment amounts. The documented acceptance fact "score category = BigWin" was never pinned by a test.

REPRODUCTION: scratch xUnit test constructing WinResult{Method=SelfDraw, Pattern=LastTileFromWall} → ScoringService.CalculateScore(...).Category == SmallWin (expected BigWin). Same for KongReplacementWin and RobbingKong.

FIX APPLIED (worktree /data/audit-main, NOT pushed/merged): extended ClassifyWin to (a) short-circuit `win.IsRobbedKong` → BigWin, and (b) add explicit BigWin cases for HeavenlyHand/EarthlyHand/LastTileFromWall/LastDiscardCatch/KongReplacementWin. Kept the Pattern-based structural switch intact for backward compat with direct-Pattern callers. Added regression test Changsha/Scoring/SpecialContextWinCategoryTests.cs. Validation: full Changsha namespace suite 681 passed / 2 skipped / 0 failed; targeted scoring+golden+robbing+special-context filter 49/49 pass (Section51GoldenTests §5.1 Examples 1-10 unaffected).

RECOMMENDATION: land the fix + regression test on a squad branch (scope: backend production code + tests). Consider also pinning ScoreResult.Category in the existing SpecialContextWinsTests.

### 2026-08-05T23-52-13: #157 root cause: ScoringService.ClassifyWin ignores contextual Big Wins + IsRobbedKong
**By:** Bishop
**What:** #157 root cause: ScoringService.ClassifyWin ignores contextual Big Wins + IsRobbedKong
**Why:** Confirmed on pristine origin/main 0dfd96a. `ScoringService.ClassifyWin(WinResult)` classifies category from `win.Pattern` alone via a switch whose default arm returns SmallWin. The WinDetector already promotes `WinDetectionResult.Category` to BigWin for contextual patterns and mirrors contextual patterns into `WinResult.AllPatterns`, but that category is dropped at the detector→WinResult boundary (WinResult carries no Category). For a Standard-shaped hand the detector sets `Pattern` to the lone contextual pattern (HeavenlyHand/EarthlyHand/LastTileFromWall/LastDiscardCatch/KongReplacementWin), which the ClassifyWin switch does not enumerate → falls to `_ => SmallWin`. RobbingKong (抢杠胡) is carried only on `WinResult.IsRobbedKong` (no WinPattern) so it is likewise missed. Result: contextual Big Wins underpay (self-draw 1/2 vs 3/4; discard 1/2 vs 6/7).

Fix seam: `ScoringService.ClassifyWin` must treat a win as BigWin when `IsRobbedKong` is true OR any Big-Win WinPattern appears in `Pattern`/`AllPatterns`. Extracting a single canonical Big-Win pattern set avoids the inconsistent duplicated classification. Payment/multiplier/zero-sum construction is unchanged; only classification is corrected.

**References:** #157, Vasquez audit, docs/rules/changsha-spec.md §4.2.2, docs/rules/changsha-spec.md §5.1
