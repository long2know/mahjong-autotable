The single most important takeaway is **pre-wire is a
discipline tax that the operator collects forever-after as
one-line PRs**. Reframing: a Phase K hardening gate is
typically TWO mechanical changes — landing the patch file +
wiring it into the kustomization — bundled into a single
cutover-day PR. The W14 split makes the patch file landing
W13 (already done) AND the kustomization wire-up W14
(commented out) — so the actual cutover-day PR is just a
comment-prefix toggle. The pre-condition verification (the
HARD part) stays the same; the mechanical work shrinks to a
diff a reviewer can audit in one glance. The pattern is
worth applying to every remaining hardening gate.

## 4. Lessons learned

### 4.1 Pre-wire-then-toggle as a pattern

Every multi-line mechanical change should be evaluated for
the pre-wire-then-toggle pattern: can the mechanical work
land one wave before the apply-day flip, with the apply-day
diff reduced to a comment toggle? If yes, the apply-day PR
is auditable in seconds; pre-condition verification gets
the operator's full attention.

The pattern doesn't apply to changes that need to be
discoverable in `kustomize build` output (e.g. a new
resource creation that the operator needs to see in plan
output before approving). It DOES apply to changes that
are a flip of an existing field value (the W14 envFrom
`optional: true → false` flip is the canonical case).

W15+ should evaluate the §6.3 Kyverno enforce gate +
§6.5 CSP enforce gate for pre-wire candidacy. The §6.4
HPA min-replicas bump is a NUMBER change (3 → 5), not a
toggle, so the pattern doesn't directly apply.

### 4.2 Survey-then-execute cadence rhythm

The W13 §6.6 survey (TF CLI bump planning) → W14 §7
actual-bump (TF CLI 1.10.5 → 1.11.4) is a two-wave rhythm
that consistently lands quarterly cadence work without
schedule slippage. The survey wave does the risk
classification + provisional recommendation; the execute
wave does the actual change. The survey output is the
audit trail for "what we considered + ruled out" and
prevents the execute wave from re-doing the analysis.

The pattern extends to the W17 Q1 2027 TF bump: W16 survey
+ W17 execute. The §6.6 W13 narrative is the template.

### 4.3 Phase pre-plan as input to cross-lane negotiation

Surfacing Phase L scope during Phase K close-out
(`docs/phase-l-devops-readiness.md`) gives the squad time
to negotiate the cross-lane dependencies before they
become critical-path blockers. Compare with Phase J → K
transition where the DevOps lane discovered the regional
cluster scope mid-Phase-K (Wave 11) and had to thread the
EDGE module + regional readiness as a series of
in-Phase-K hand-offs.

The Phase L pre-plan is the input to a future "Phase L
charter" memo (likely landing at Phase K close-out — W17
or W18). Other lanes should produce their own Phase L
pre-plans before the charter memo. The W14 doc is the
prompt.

### 4.4 Renumber discipline in docs

The `docs/jwt-rotation-rehearsal.md` §5 → §11 renumber
required a single internal cross-reference update (§3.2's
"see §8 Failure scenarios" → "see §9 Failure scenarios").
The W14 renumber missed NO references; the discovery was
via `grep -nE "§[5-9]|§10"` on the post-edit file.

The discipline: ALWAYS grep for the old section numbers
after a renumber; cite the grep output in the wave's
memo as evidence. The W14 §3 history's commit message
should note "renumber + cross-reference update verified
via grep".
