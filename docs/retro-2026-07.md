# Monthly retro — July 2026 (Phase K, Wave 8)

> Author: Apone (DevOps)
> Period: 2026-07-01 → 2026-07-31 (W7 merged 2026-06-30 closes
> the June 2026 retro; W8 bringup runs through July).
> Cadence: monthly. July sits inside Q3 2026 — the next
> quarterly DR rehearsal report (§3a in the September retro) is
> automated by the W8 workflow.

This retro covers Phase K Wave 8. The dominant theme is
**production-track hardening + edge cutover staging**: the W7
edge module's staging-env instantiation (the cutover runbook
that gets prod's edge surface to a known-good state before W9's
prod-WAF `count`→`block` flip), CI parity on the W7 pre-commit
hooks (a `--no-verify` workaround no longer reaches `main`),
kyverno-enforce-patch canonical-path reconciliation (the W7
doc surface drifted from the actual on-disk path; the W8 guard
fails loudly on the drift mode), the mobile **Production**
release surface (App Store + Play Production after the W7
External Testing surface), Helm canary via Argo Rollouts
(5%→20%→50%→100% with Prometheus analysis — staging-only for
W8), and DR rehearsal automation (the W6 manual runbook is now
a quarterly `workflow_dispatch`).

The single most important takeaway is **§3.3 — the kyverno-path
drift mode**. The W7 invariant script registered the canonical
path (`infra/k8s/overlays/prod/kyverno-enforce-patch.yaml`); the
W7 doc registered a wrong path (`infra/k8s/policies/kyverno-enforce-patch.yaml`)
in two places. That asymmetry means a follow-up commit
authored against the doc-listed path would land a file at the
wrong location, the invariant script's regex extractor would
match zero strings (because the file at the canonical path is
unchanged), and the script would "pass" — a silent admission-
policy regression. W8 closes the hole with a presence-check
guard and the doc fix; W9 should audit the OTHER cross-file
invariants for the same drift shape.

## 3. Lessons learned

### 3.1 The `flock`+per-invocation-identity pattern survived another wave

W7's retro §3.1 documented this. W8 confirmed: zero cross-
lane commit races on a wave with **four** parallel lanes
(Apone DevOps, Bishop backend, Vasquez QA, plus the partner
chart consumer's lane). The `flock -w 120 9` ceiling held
across all observed lane interleavings; the
`-c user.name=... -c user.email=...` flags continue to attach
the right author without leaking lane identity into shared
config.

The one new observation: when **two** lanes both want to push
to the same branch in rapid succession, the second push
non-fast-forwards. Mitigation: each lane fetches before its
push. W9 should add a `git fetch + git rebase` step inside
the `flock` critical section as a belt-and-braces guard.

### 3.2 Argo Rollouts vs Flagger — the drop-in argument

W7's `helm-charts.md` left the canary engine as TBD. W8
picked Argo Rollouts. The decisive factor:

* **Argo Rollouts** — the `Rollout` CRD is a drop-in for
  `Deployment` (same `spec.template`, same selector model).
  An operator who can edit a Deployment can edit a Rollout.
  No service-mesh dependency for replica-based canary; only
  needed for traffic-split canary (nginx-canary annotations
  are the upgrade path).
* **Flagger** — better at traffic-split out of the box (it
  drives Istio / Linkerd / nginx-canary natively), BUT
  requires an existing service-mesh OR a sidecar injector.
  We don't run a mesh in W8.

Plus: Argo Rollouts is the same vendor as Argo CD (the W10
GitOps target). Picking Rollouts now means one vendor to
learn, not two.

### 3.3 The kyverno-path drift mode

Documented in §3 above and §6.6 of `docs/admission-policy.md`.
The shape of the bug:

1. W7 invariant script registered the canonical path
   (`infra/k8s/overlays/prod/kyverno-enforce-patch.yaml`).
2. W7 doc (`docs/admission-policy.md` §6) referenced the
   wrong path (`infra/k8s/policies/kyverno-enforce-patch.yaml`)
   in two places.
3. A hypothetical follow-up commit authored against the doc
   would land a duplicate file at the wrong path.
4. The duplicate file would be the one applied by an
   operator who followed the doc (because they would `kubectl
   apply -f` the doc-listed path, not the canonical one).
5. The invariant script's regex extractor would still match
   the canonical-path file (unchanged); the extractor would
   never look at the wrong-path file; the script would
   "pass".
6. The cluster would silently regress to the W6 admission
   policy (the wrong-path file is the older draft).

W8 closes the hole TWO ways:
* **Doc fix** — `docs/admission-policy.md` now references
  the canonical path in both places.
* **Presence-check guard** — `scripts/check_signer_identity.py`
  fails loudly if the wrong-path file reappears.

The W9 follow-up is to audit the OTHER cross-file invariants
for the same drift shape. Candidates:
* The `Auth.JwtRsaKeys` array index ↔ SSM parameter name
  binding (the W4 → W7 rotation drift mode).
* The six signer-identity surfaces (covered by the W7
  invariant guard, but the doc surface for each one is
  independently maintained — a doc drift on any of the six
  is the same shape as the kyverno path drift).

### 3.4 CI parity on local-only pre-commit hooks

The W7 hook ran locally; W8 added the CI parity gate. Two
observations:

* The local hook ran fast (~2s for the invariant script + ~3s
  for the standard hooks). The CI run is ~30-45s cold and
  ~5s warm with the `~/.cache/pre-commit` cache. The warm
  case is the dominant CI cost because branch pushes mostly
  re-use the same hook config across consecutive commits.
* The local hook + CI hook are NOW the same hook list. A
  divergence (e.g., adding a hook to `.pre-commit-config.yaml`
  without re-running `pre-commit install` on the dev
  machine) is caught by CI on the next push. The
  documentation in `docs/signer-identity-invariant.md` §5.2
  emphasises that the source of truth is the config file,
  NOT the installed git hook.

### 3.5 Staging WAF `COUNT` mode is the right default

The W7 module shipped with `BLOCK` as the only behaviour
because it was prod-only. W8 added the `waf_managed_rules_action`
variable defaulting to `COUNT` in staging. The rationale:

* The managed rule groups (AWS-managed `CommonRuleSet`,
  `KnownBadInputsRuleSet`, etc.) sometimes fire on legitimate
  staging traffic (Vasquez's test fixtures use synthesised
  payloads that can trip the SQLi rule). In `BLOCK` mode,
  staging would take a self-inflicted outage from each
  false-positive.
* `COUNT` records the would-be block to CloudWatch + the
  S3 WAF log bucket without serving a 403. The same Athena
  workgroup from W7 surfaces the COUNT events; the operator
  can review them on the same schedule as prod's BLOCK
  events.
* The W11 prod-flip criteria: a quarter of soak with **zero**
  unexpected COUNT events on staging.

This is a generally-applicable pattern: any new WAF rule
group should land in COUNT first, soak for a known interval,
THEN flip to BLOCK. The new `waf_managed_rules_action`
variable makes this the path of least resistance.

### 3.6 The DR rehearsal artefact-vs-commit boundary

W8's DR rehearsal workflow generates `docs/dr-rehearsal-results-YYYY-Q#.md`
but does NOT push to the repo. The workflow's OIDC role has
`contents: read` only; pushing would require `contents:
write`, which would also expand its blast radius to anything
else the role could touch.

The trade-off: the operator manually commits the result file
after the rehearsal. Slightly more friction, but the OIDC
role stays minimum-privilege AND the operator gets a final
review of the report before it lands in the doc tree.

The alternative (a separate `dr-results-bot` write-scoped
OIDC role) was rejected: it doubles the OIDC role surface
for a once-a-quarter operation.
