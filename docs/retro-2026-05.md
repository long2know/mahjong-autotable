## 3. Lessons learned

### 3.1 The Wave-5 `.git/config` race incident — permanent reference

**What happened.** Apone's Wave-5 commit `b346157` ("Phase K Wave 5
— DevOps bringup …") accidentally absorbed Hicks's frontend
changes alongside the DevOps changes. The commit landed under the
correct author (`Apone (DevOps) <apone@squad.mahjong>`) but its
diff included unrelated lane work.

**Root cause.** The Wave-5 recovery sequence used the stateful
form of git author configuration:

```bash
# ANTI-PATTERN — DO NOT USE
git config user.name "Apone (DevOps)"
git config user.email "apone@squad.mahjong"
# … other commands …
git add <DevOps paths>
git commit -m "Phase K Wave 5 — …"
```

`git config` writes to `.git/config`. A concurrent squad agent
running in the same working tree rewrote `.git/config` to its own
identity between the `git config` calls and the `git commit`. The
race window was open for the duration of the intervening
commands. In addition, the `git add` step (also racy across
agents) inadvertently staged frontend changes that another agent
had left in the working tree.

There were two distinct race surfaces in play:

1. **`.git/config` identity race.** Two agents writing to the
    same `.git/config` between commit-prep and commit.
2. **Working-tree staging race.** Two agents with overlapping
    pathspecs in `git add` — even
    if each uses narrow pathspecs (we DID use narrow pathspecs in
    W5), if Agent A's add and Agent B's add interleave they can
    each stage what the other has touched.

**W6 mitigation pattern — IN FORCE FROM WAVE 6 ONWARD.** The
remediation has three parts. ALL THREE must be followed; any one
on its own is insufficient.

1. **Per-invocation identity, never stateful.** Use
    `git -c user.name="<Agent (Lane)>" -c user.email="<agent>@squad.mahjong" commit -m "…"`
    on every commit. Do NOT run `git config user.name "…"` /
    `git config user.email "…"` as a setup step. The `-c` flags
    are atomic per `git commit` invocation; there is no window
    where another agent can race the identity state.

2. **`flock`-wrapped commit + push.** Any commit + push pair must
    run inside a `flock` on a shared lock file so two agents
    cannot run a `git commit && git push` pair concurrently:

    ```bash
    ( flock -w 120 9 || exit 1
      git status --short | head -20            # see step 3
      git add <NARROW pathspecs, by lane>
      git -c user.name="Apone (DevOps)" \
          -c user.email="apone@squad.mahjong" \
          commit -m "Phase K Wave 6 — …"
      git push origin stlong/phase-k-wave-6-bringup
    ) 9>/tmp/squad-git-lock
    ```

    The `flock` serialises critical sections across agents. The
    `-w 120` timeout gives a generous wait window — if it
    expires, the agent fails closed rather than landing a racy
    commit.

3. **`git status --short` pre-check before every `git add`.** Inside
    the `flock` critical section, BEFORE staging, dump the
    short-format status and verify that only files in the
    agent's lane are present. If unexpected files are listed
    (other agents' work-in-progress), the commit MUST be
    aborted; the operator decides whether to stash, re-route,
    or wait. This catches the working-tree staging race even
    when `git add` is given narrow pathspecs.

**Per-lane staging rules in force from W6.** Apone (DevOps) stages
ONLY: `.github/workflows/`, `infra/`, `docs/{slsa,hsts,turn,admission,oauth,jwt-rotation,production-deployment-runbook,kubernetes,terraform,secrets-scanning,voice-sfu-design,mobile-release,retro-2026-MM}.md`,
`tests/{load,smoke}/`, `Dockerfile*`, `CHANGELOG.md`, `mobile/`,
`.squad/agents/apone/`, `.squad/decisions/inbox/apone-*`. Other
agents have analogous narrow pathspec lists in their own
agents/`history.md`. The lists are union-disjoint by lane.

**Author verification gate.** After every commit, the commit
SHA must be verified with
`git log -1 --pretty='%an <%ae>' <SHA>` against the expected
agent identity. The W6 memo's hand-off section reports this
verification. Any mismatch is treated as an incident.

This pattern is also documented in this wave's
`.squad/decisions/inbox/apone-phase-k-wave-6.md` §1.6 and in
the Wave 6 entry of `.squad/agents/apone/history.md`.

### 3.2 The Wave-4 → Wave-5 sequencing lesson

The Wave-5 Kyverno `attestations:` block intentionally REJECTS
Wave-4 images (they're signed with the container-generator's
identity, not the generic generator's). This was the right call
— policy + workflow refactor ship in the SAME wave — but it
requires a coordinated rollout (publish Wave-5 image first; then
re-apply the policy). Carrying this lesson into Wave 6: the
mobile-release tag prefix (`mobile-v*.*.*`) is deliberately
distinct from the backend `vX.Y.Z` tag so future mobile tag
events cannot trigger backend release workflows or vice versa.

### 3.3 Lock-step invariants are growing — track them centrally

W4 had four lock-step files (signer URL canonical list); W5
took it to six (added the Kyverno `attestations:` block
identity-pin + the `docs/slsa-provenance.md` `--source-uri`
mention). W6 introduces a NEW lock-step pair: the
`modules/github-oidc/main.tf` policy and `least-privilege.tf`
rationale. Two-file lock-step pairs are easier to keep aligned
than six-file lists; for the six-file signer list, consider a
Wave-7+ pre-commit hook that greps for the canonical URL and
fails if any one file drifts.
