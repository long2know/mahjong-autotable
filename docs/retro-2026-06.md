This retro covers Phase K Wave 7. The dominant theme is **edge
+ release-distribution surfaces**: Helm chart-of-charts (the
operator-driven install path running parallel to Kustomize),
the public-facing edge Terraform module (Route53/ACM/WAFv2/opt-in
CloudFront), GHCR→ECR signature-preserving mirroring, mobile
External Testing promotion (TestFlight External + Play Closed),
the six-file signer-identity invariant pre-commit hook, and
RS256 JWT SSM provisioning paving the way for Bishop's W7
backend RS256 cutover + the W8 JWKS surface.

`alias:` quirk**. The trap (Helm routes umbrella values to
subcharts by chart NAME unless `alias:` is set) cost a real
debugging session during the W7 chart bringup; documenting it
saves the W8 partner-chart consumers from rediscovering it.

## 3. Lessons learned

### 3.1 The `flock`+per-invocation-identity pattern survived another wave

W5's `.git/config` race incident motivated the per-invocation
identity + `flock`-wrapped commit/push pattern. W6 reaffirmed
it; W7 added Apone-lane evidence:

* Apone's W7 commit cluster passed `git log -1 --pretty='%an
  <%ae>' <SHA>` on every commit (`Apone (DevOps) <apone@squad.mahjong>`).
* No `git config user.name "…"` step appears anywhere in W7
  history.
* The pattern is now muscle memory; the squad lost <5 min total
  to git-config-related friction across the entire W7 run.

The W5 retro §3.1 reference is canonical. W7 carried no
diversification — the lesson stuck.

### 3.2 Helm umbrella `alias:` quirk

The W7 chart-of-charts bringup hit a non-obvious Helm behaviour:
**Helm routes umbrella `values.yaml` to subcharts BY CHART NAME
unless `alias:` is set on the dependency.** Our subcharts are
named `mahjong-api`, `mahjong-coturn`, `mahjong-postgres-sidecar`
but the umbrella values use short keys (`api`, `coturn`,
`postgresSidecar`) for readability. Initial bringup produced a
prod render with PVCs despite `api.persistence.enabled: false`
— the override was silently ignored because helm was looking
for `mahjong-api.persistence.enabled`.

Mitigation:

* Add `alias: <short-key>` to EVERY dependency in the umbrella
  `Chart.yaml`. The short key is what umbrella `values.yaml`
  uses; the canonical `name:` (matching the subchart's own
  `Chart.yaml`) is what `dependencies update` resolves against.
* Document the trap in `docs/helm-charts.md` §1.1 so the W8
  partner-chart consumers don't rediscover it.

Detection cost: ~10 min of "why is this PVC still rendering?"
puzzlement. Cheap because the prod render was visually
inspected as part of the W7 acceptance gate; would have been
expensive if it had landed at deploy time.

### 3.3 Terraform `configuration_aliases` standalone-validation
caveat

Modules that declare `configuration_aliases = [aws.X]` cannot
be validated standalone with `terraform validate` — the
validator expects every declared provider to be supplied by a
caller. The W6 `dr-replication/` module had this; W7 `edge/`
hit the same. Both modules now have a documented test-rig
pattern at `.work/tf-edge-validate/main.tf` (a tiny standalone
module that instantiates the target module with mocked
provider credentials).

The pattern:

```hcl
provider "aws" {
  region                      = "us-east-1"
  skip_credentials_validation = true
  skip_metadata_api_check     = true
  skip_requesting_account_id  = true
}

provider "aws" {
  alias                       = "us_east_1"
  region                      = "us-east-1"
  skip_credentials_validation = true
  skip_metadata_api_check     = true
  skip_requesting_account_id  = true
}

module "edge" {
  source = "../../infra/terraform/modules/edge"
  providers = {
    aws            = aws
    aws.us_east_1  = aws.us_east_1
  }
  # ... required inputs ...
}
```

Documented in `docs/terraform.md` §5.4. The rig itself is NOT
committed (it lives under `.work/` which is gitignored
session scratch); the rig PATTERN is the artefact.

### 3.4 Signature-preserving mirroring needs `crane copy`, not
`docker pull` + `docker push`

The naive mirroring path (`docker pull <src> && docker tag &&
docker push <dest>`) is a known footgun: dockerd re-encodes the
gzip stream on push, producing different layer digests →
different manifest digest → cosign sidecar (`.sig`) at the
destination doesn't resolve → image admission fails closed.

W7's mirror workflow uses `crane copy` (registry-to-registry
HTTP-only copy; no decompression/re-compression) for the
manifest and `cosign copy` for the sidecars. The W7
verification step checks `crane digest <dest>` equals
`crane digest <src>` before the cosign sigs are copied — the
guard catches any future regression where someone "fixes" the
workflow with a docker-based path.

Documented in `docs/ghcr-to-ecr-mirror.md` §2.

### 3.5 Six-file signer-identity invariant — automated guard
finally landed

The W5 incident motivation: a JWT-related PR moved the cosign
verify step from `verify-signature.yml` to an inline step in
`sign-image.yml` and forgot to update verify-signature.yml's
default input. Local cosign verify worked (sign-image.yml was
consistent), the cluster's Kyverno policy was fine, but the
scheduled image-rescan job started rejecting EVERY image —
~25 min outage of the rescan alerting before a human noticed.

W6 documented the four-file lock-step inline. W7 promotes the
documentation into an automated guard
(`scripts/check_signer_identity.py`) + extends the set to six
files (the slsa-provenance workflow + the slsa-provenance doc
now participate too). The hook is wired in pre-commit as
`always_run: true, pass_filenames: false` because drift is a
cross-file property — staged-file scoping would miss drift
introduced via a partial commit.

Drift-detection smoke test passes (mutating
`infra/k8s/policies/kyverno-cosign-verify.yaml` in memory and
re-running the hook → exit 1, "DRIFT" in stdout).

### 3.6 SSM separation-of-concerns for HS256 vs RS256 JWTs

Initial W7 design considered extending the W4
`mahjong-jwt-keys` Secret with RSA entries (one Secret, two
algorithm families). Decision: **separate Secrets** — one per
algorithm family. Rationale:

* HS256 and RS256 differ in cryptographic shape (opaque bytes
  vs PEM); a single Secret would force the W7 binding's value
  parser to disambiguate per-index.
* Rotation cadences differ — HS256 30-day, RS256 90-day (JWKS
  cache TTLs make tighter RS256 rotation pointless and
  bandwidth-wasteful).
* Bishop's W7 binding consumes a NEW config section
  `Auth:JwtRsaKeys`; keeping it on its own data plane lets the
  existing `Auth:JwtSigningKeys` binding stay untouched —
  smaller blast radius if the W7 binding has a bug.

Documented in the per-file headers of the two new ESO manifests
and in `docs/jwt-rotation.md` §8.3 (rewritten this wave).

## 3a. DR rehearsal report (Q2 2026 — quarterly)

June is the quarterly retro for Q2 2026. The W6 DR module
shipped on 2026-06-04; a partial rehearsal was completed
on **2026-06-08** (in the W7 setup window before the W7
bringup commits started).

### 3a.1 Scope of the rehearsal

* Tabletop walkthrough of the W6 DR runbook
  (`docs/terraform.md` §4) — operator stepping through each
  command without executing the destructive ones.
* Live execution of NON-DESTRUCTIVE pieces:
  * `aws rds describe-db-instances --region us-west-2 --db-instance-identifier mahjong-prod-replica` — verified replica exists, lag <30 s, status `available`.
  * `aws ecr describe-images --region us-west-2 --repository-name mahjong-autotable` — verified images present, ~3 min replication lag against us-east-1 push timestamps.
  * `aws route53 get-health-check --health-check-id <primary>` — verified the primary `/health` check is `Success` with the W6-pinned TTL<60s.
* SKIPPED (destructive — only run in a real DR event or a
  scheduled annual rehearsal): RDS replica promotion,
  Route53 failover-record activation, full app-side cutover.

### 3a.2 Findings

* **The W6 6-output convention pays off.** The runbook's
  `terraform output -raw failover_record_fqdn` etc. avoids
  hand-plumbed ARNs in the rehearsal commands; operator can
  copy-paste from the runbook directly.
* **Route53 health-check threshold MAY need tightening.** The
  W6 default is 3 consecutive failures at 30 s intervals →
  ~90 s detection latency. For the Phase K reliability target
  (≤120 s failover) this is OK; if Phase L tightens to ≤60 s
  the threshold needs to go down. Logged as an Action Item
  (§4.2).
* **The `dr-replication/` module declares no
  `data.aws_caller_identity` block.** The runbook's "verify
  you're running against the right account" step relies on
  the operator's terminal-side `aws sts get-caller-identity` —
  no in-Terraform guard. Acceptable for a runbook-driven
  procedure; flagged as a candidate W9 hardening.
